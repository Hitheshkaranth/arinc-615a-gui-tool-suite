## 02 — One core, two front ends
The tree contains two application sections that never reference each other. They meet only at `lib/arinc_615a`.

| Concern | Command-line section | Graphical section |
| --- | --- | --- |
| Parameter capture | boost::program_options | QWizardPage::isComplete() |
| Dispatch | Commands::CommandRegistry | QAction → slot |
| Progress reporting | std::cout | Qt signals into table models |
| Completion rendezvous | std::latch | queued signal, no blocking |
| I/O thread | std::jthread | std::jthread |
| Abort path | SIGINT → boost::signals2 | toolbar button → direct slot |
| Extra dependencies | commands | Qt 6, qt_icon_resources |

The interesting column is the fourth. The CLI blocks its command thread on `done.wait()` until the protocol callback counts the latch down; the process exists to run exactly one operation, so blocking is free. The GUI cannot block — its thread is the event loop — so every completion path is a queued signal and the wizard's *Finish* button is what "waiting" looks like to the operator.

That difference, and the fact that Qt widgets have thread affinity, is the whole substance of the adapter layer in §7.

## 03 — Five layers on the GUI side
Reading downward, each layer knows only the one below it. The upward path is always a Qt signal or an abstract handler interface bound at construction.

| Layer | Where | Responsibility |
| --- | --- | --- |
| Application | app/arinc_615a_data_loader_gui | Register resources, construct `QApplication`, show the main window |
| Shell | arinc_615a_dla_qt/DataLoaderMainWindow | Owns the `io_context`, the FIND client, the host protocol, configuration, the target list and the media set manager |
| Wizards | arinc_615a_dla_qt/{find,information,upload,download} | Collect parameters, show live status, present the result |
| Adapters | arinc_615a_dla_qt/operations | Implement the core's handler interfaces; convert every callback into a Qt signal |
| Models | arinc_615a_qt | `QAbstractTableModel` subclasses over ARINC 615A value types |

Below the shell sits the protocol core, unchanged and unaware that a GUI exists. `Arinc615a::Host::Protocol::instance( ioContext )` is the same call the CLI makes; `Arinc615a::Find::Clients::Client::instance( ioContext )` likewise.

#### Library dependencies

## 04 — Two threads and a queued connection
The process runs two threads for the whole of its life.

1. **The Qt GUI thread** — the main thread. Runs `QApplication::exec()`. Owns every widget, every model, and every wizard.
2. **The ASIO I/O thread** — a `std::jthread` started at the end of the `DataLoaderMainWindow` constructor, running `ioContext.run()`. Owns every socket. All protocol handler callbacks arrive here.

A `boost::asio::executor_work_guard` is constructed before the thread starts, so `run()` does not return when the queue drains between operations. The destructor sequence is `workGuard.reset()` then `ioThread.join()`, then configuration is saved.

Everything crossing from the I/O thread to the GUI thread crosses as a `Qt::QueuedConnection`. The connections are written explicitly rather than left to `Qt::AutoConnection` — for example in `InformationOperationWizard`, every one of the six `connect()` calls that binds an adapter signal names `Qt::QueuedConnection` at the call site.

> **Why explicit**  
> `Qt::AutoConnection` decides direct-versus-queued by comparing the *emitting* thread against the receiver's thread affinity at emit time, which would give the right answer here anyway. Naming the type explicitly documents the boundary and stops a later refactor from silently turning a cross-thread call into a direct one.

Queued delivery copies the arguments, so every payload type must be registered with the meta-object system. Each adapter's constructor does this up front:

```cpp
qRegisterMetaType< std::chrono::seconds >( "std::chrono::seconds" );
qRegisterMetaType< std::string >( "std::string" );
qRegisterMetaType< Arinc615a::StatusCode >( "Arinc615a::StatusCode" );
qRegisterMetaType< Arinc615a::Information::InitializationResponse >(
  "Arinc615a::Information::InitializationResponse" );
qRegisterMetaType< Arinc615a::Information::InformationStatus >( "Arinc615a::Information::InformationStatus" );
qRegisterMetaType< Arinc615a::Information::TargetsHardware >( "Arinc615a::Information::TargetsHardware" );
```

Note the signal signatures that follow from this. The handler interface hands `finished()` a `std::string_view`; the signal takes `const std::string &`. It has to — a view into a buffer owned by the I/O thread would dangle by the time the GUI thread dequeues the event. The adapter's one-line body `emit operationFinished( code, std::string{ description } )` is where that copy happens.

## 06 — DataLoaderMainWindow: what it owns
`lib/arinc_615a_dla_qt/DataLoaderMainWindow.cpp:60`. The constructor is 130 lines and does six things in order.

1. **Member init list** constructs the four owned dialogues, six statistic models, the `executor_work_guard` over `ioContext`, and — critically — `findClient` and `protocol` from that same `ioContext`. Both core instances exist for the lifetime of the window, not per operation.
2. **`ui->setupUi( this )`** then binds each of the six statistic models to its table view and sets every horizontal header to `ResizeMode::Stretch`.
3. **About dialogue** is populated with the product logo, name, version, licence and URL from `Arinc615a::Version`, plus a version list covering ARINC 615A, TFTP, ARINC 665, ARINC 649, qt_icon_resources, helper, Boost and Qt.
4. **`loadConfiguration()`** reads `DataLoader.json` and `Targets.json` from the Qt application configuration location.
5. **`loadMediaSetManager()`** starts the ARINC 665 media set scan asynchronously — see below.
6. **Action wiring**, then the I/O thread is started last.

#### The six statistic models

The central widget is nothing but three group boxes, each holding an RX and a TX table: TFTP packets, ARINC 615A FIND packets, ARINC 615A protocol files. They are fed by `updatePacketStatistic()` at `DataLoaderMainWindow.cpp:477`, which pulls six process-global counters:

```cpp
rxTftpPacketStatisticModelV->statistic( Tftp::Packets::PacketStatistic::globalReceive().statistic() );
txTftpPacketStatisticModelV->statistic( Tftp::Packets::PacketStatistic::globalTransmit().statistic() );
rxFindPacketStatisticModelV->statistic( Arinc615a::Find::Packets::PacketStatistic::globalReceive().statistic() );
txFindPacketStatisticModelV->statistic( Arinc615a::Find::Packets::PacketStatistic::globalTransmit().statistic() );
rxProtocolFileStatisticModelV->statistic( Arinc615a::Files::ProtocolFileStatistic::globalReceive().statistic() );
txProtocolFileStatisticModelV->statistic( Arinc615a::Files::ProtocolFileStatistic::globalTransmit().statistic() );
```

These are the same globals the CLI prints after each operation. The refresh is **not** on a timer: it is connected to each wizard's `finished` signal, so the tables update when a wizard closes and at no other time. That is a deliberate choice — polling process-global counters from a timer would read them concurrently with the I/O thread writing them.

#### Asynchronous media set loading

`loadMediaSetManager()` at line 396 is the one place the shell does real work at startup. It disables *Upload Operation* and *Manage Media Sets*, constructs an `Arinc665Qt::Actions::LoadMediaSetManagerAction` and a `QProgressDialog`, wires three signals — progress, loaded, failed — and then kicks the action off with:

```cpp
QMetaObject::invokeMethod(
  mediaSetManagerLoader,
  &Arinc665Qt::Actions::LoadMediaSetManagerAction::start,
  Qt::ConnectionType::QueuedConnection );
```

A queued invocation onto the object's own thread, which defers `start()` until control returns to the event loop — after the constructor has finished and the window is shown. Both success and failure lambdas call `deleteLater()` on the action and the dialogue; the failure lambda additionally shows the media set directory in the error text and then calls `close()` on the window.

Upload is the only operation that needs the media set manager, which is why it is the only action gated on the scan completing.

## 07 — How a callback becomes a signal
`lib/arinc_615a_dla_qt/operations/` holds five classes — `FindQuery`, `InformationOperation`, `UploadOperation`, `MediaDefinedDownloadOperation`, `OperatorDefinedDownloadOperation`. Each has the same shape:

```cpp
class InformationOperation final :
  public QObject,
  private Arinc615a::Host::InformationOperationHandler
{
    Q_OBJECT
  ...
};
```

Public `QObject`, **private** handler interface. The private inheritance is the point: the handler methods are an implementation detail that only the protocol core is allowed to call, and it gets that right through `.handler = *this` in the operation configuration. Nothing in the GUI can invoke them.

The class exposes two slots — `startOperation()`, `abortOperation()` — plus operation-specific ones such as `transmitLoads()` or `transmitFiles()`, and a set of signals mirroring the handler methods one-for-one.

| Handler method (I/O thread) | Signal (queued to GUI thread) |
| --- | --- |
| initialisationDeferred( seconds ) | operationDeferred( seconds ) |
| initialisationResponse( response ) | operationInitialised( response ) |
| finished( code, string_view ) | operationFinished( code, std::string ) |
| status( status ) | receivedStatus( status ) |
| targetInformation( hw, integrity ) | receivedInformation( hw, integrity ) |

Most of the bodies are exactly one line. `InformationOperation::status()` is `emit receivedStatus( status );` and nothing else. That is the design working: the adapter has no state machine of its own, it is a thread-boundary marshaller.

#### Where a slot does more than emit

`startOperation()` is the exception. Taking `InformationOperation::startOperation()` at `operations/InformationOperation.cpp:49`:

```cpp
operationV = protocolV->informationOperation(
  Arinc615a::Host::InformationOperationConfiguration{
    .dataLoaderConfiguration = configurationV.dataLoaderConfiguration,
    .handler = *this,
    .targetAddress = targetAddress,
    .targetId = targetId,
    .dlpTimeout = configurationV.dlpTimeout,
    .portOption = configurationV.portOption } );
operationV->start();
```

Compare the CLI's `InformationOperationCommand::execute()`, which builds the identical designated initialiser from `boost::program_options` values and then blocks on `done.wait()`. Same struct, same core call; the GUI simply returns to the event loop instead of waiting.

The catch block on each of these slots raises a `QMessageBox::critical` and then emits `operationFinished( StatusCode::OperationAbortedByDlp, "Error During Operation" )`, so a construction failure still moves the wizard to its completed page rather than leaving it stuck on a status page with no way forward.

#### Abort

`abortOperation()` null-checks `operationV` and calls `abort( AbortReason::Operator )`. Per the core's contract this only sets a flag; the request goes out with the next status file the target asks for. The CLI reaches the same call through a `boost::signals2` connection driven by `SIGINT`; the GUI reaches it from a button, with no signal machinery in between.

## 08 — The shape every wizard shares
All four operation wizards are `QWizard` subclasses laid out in Qt Designer, with the pages declared as promoted widgets in the `.ui` file. Each constructor follows the same seven steps.

1. Construct the adapter as a child `QObject`, so it dies with the wizard.
2. `ui->setupUi( this )`.
3. Push context onto the settings page — the target list always, plus media sets for upload or a download base directory for the download wizards.
4. `setButtonText( CustomButton1, tr( "Abort Operation" ) )`.
5. Load the operation's SVG from the resource archive and set it as `LogoPixmap` at 64 px on *every* page, by iterating `pageIds()`.
6. Connect settings-page selection signals up to the wizard, and the status page's start/abort signals down to the adapter.
7. Connect each adapter signal to the pages that render it, always with `Qt::QueuedConnection`.

Step 7 routinely fans one signal out to several receivers. In `InformationOperationWizard`, `operationFinished` goes to three places at once — the wizard itself (to swap the button set), the status page (to stop the spinner) and the completed page (to render the final status code). No receiver knows about the others.

Wizards are heap-allocated and self-disposing. The shell's `findQuery()` slot is the template:

```cpp
auto * const wizard{ new FindQueryWizard{ findClient, configuration, targetsV, this } };

connect( wizard, &FindQueryWizard::finished, wizard, &FindQueryWizard::deleteLater );
connect( wizard, &FindQueryWizard::finished, this, &DataLoaderMainWindow::updatePacketStatistic );

wizard->show();
```

`show()`, not `exec()` — the wizards are modeless, so several operations can be open at once and the main window stays live behind them.

#### Page roles

| Page | Role | Commit page? |
| --- | --- | --- |
| Settings / Select address | Target selection and operation parameters; gates *Next* through `isComplete()` | Yes |
| Select files | Operator-defined download only — names the files to request | Yes |
| Status | Live status log, ratio, exception timer, per-file or per-load table | — |
| Completed | Final status code and description, part numbers or file list | — |

Marking the settings page a commit page is what makes the operation irreversible at the right moment: once *Commit* is pressed the wizard cannot go back, which matches a protocol operation that has already put a packet on the wire.

## 09 — Discovery: one broadcast, N answers
The simplest of the five, and the only one that does not go through `Host::Protocol`. Two pages: *Select Address* and *Results*.

#### Page 1 — Select Address

`find/FindQuerySelectAddressPage.cpp`. The constructor populates an editable combo box with the global IPv4 broadcast address, then every interface broadcast address Qt can see:

```cpp
ui->targetAddress->addItem( QHostAddress{ QHostAddress::SpecialAddress::Broadcast }.toString() );
for ( const auto &networkInterface : QNetworkInterface::allInterfaces() )
{
  for ( const auto &addressEntries : networkInterface.addressEntries() )
  {
    if ( addressEntries.broadcast().protocol() == QAbstractSocket::IPv4Protocol )
    {
      ui->targetAddress->addItem( addressEntries.broadcast().toString() );
    }
  }
}
```

This is the one place the GUI genuinely beats the CLI on ergonomics. The CLI's equivalent is `targetAddress( &targetAddressV, true )`, which defaults to the global broadcast and leaves the operator to work out the right per-interface broadcast address by hand on a multi-homed host.

Validation lives in `isComplete()` at line 53, which runs `boost::asio::ip::make_address_v4` on the current text and returns `false` on error — so *Commit* stays greyed until the text parses as IPv4. IPv6 is rejected by construction, which is correct: ARINC 615A FIND is a broadcast protocol and has no IPv6 form.

#### Page 2 — Results

The page starts the query on entry and renders responses into a `TargetsInformationModel`. The adapter, `operations/FindQuery.cpp:37`, configures the core query with the fluent setter chain and starts it:

```cpp
queryV = findClientV->query();
queryV
  ->responseHandler( std::bind_front( &FindQuery::findResponse, this ) )
  .completionHandler( std::bind_front( &FindQuery::finished, this ) )
  .localAddress( configurationV.findConfiguration.localInterfaceAddress )
  .remoteAddress( targetAddress )
  .port( configurationV.findConfiguration.findPort )
  .dynamicLocalPort( configurationV.dynamicFindPort )
  .timeout( configurationV.findTimeout );
queryV->start();
```

Line for line the same chain as `FindQueryCommand::execute()` in the CLI, with configuration fields substituted for parsed options. `findResponse` and `finished` each emit and do nothing else; the wizard's queued slots do the rest.

On accept, `saveResult()` checks the `AddToTargetList` wizard field and, if set, appends the model's contents to the shell's target list — which is then written to `Targets.json` when the window closes. That is the GUI's substitute for the CLI's `--targets-list` JSON file, and the two use the same on-disk representation, so a list built in one is readable by the other.

> **Observed**  
> A query against `255.255.255.255` on a network with no ARINC 615A target hardware completes after the 3 s default receive timeout with an empty results table and *Finish* enabled. Closing the wizard leaves one row in the FIND TX statistic: `Information Request / 1 / 4`. That is the full round trip — wizard, adapter, core, socket, timer, completion handler, queued signal — with the only missing element being a target that answers.

## 10 — Information: the reference operation
Three pages — settings, status, completed — and the shortest adapter of the four that use `Host::Protocol`. If you read one operation to understand the pattern, read this one.

The settings page takes the target list and lets the operator pick a target; selection emits `targetSelected( address, targetId )`, which the wizard caches in two members. Entering the status page calls `startOperation()`, which forwards those two members to the adapter slot shown in §7.

From there the wizard is entirely reactive. Four adapter signals drive it:

| Signal | Rendered by | As |
| --- | --- | --- |
| operationDeferred | status page | A synthetic `OperationDeferred` initialisation response, so a WAIT looks like any other status |
| operationInitialised | status page | Initialisation code and description |
| receivedStatus | status + completed | Appended to an `InformationStatusLogModel`; counter, code, description, exception timer, estimated time |
| receivedInformation | completed | `TargetsHardwareModel` and `PartNumbersModel`, plus an integrity indicator |

Note that both the status page and the completed page subscribe to `receivedStatus`. The status page shows the live tail; the completed page accumulates the whole log so the operator can scroll back after the operation ends. Neither knows the other exists.

The CLI's equivalent output is six `std::cout` blocks in `InformationOperationCommand` — the same fields, printed as they arrive and gone when the terminal scrolls. The information content is identical; only the retention differs.

## 11 — Upload: host as file server
The only operation gated on the ARINC 665 media set manager, and the only one where the host serves files rather than requesting them.

The settings page takes both the target list and the loaded media sets. The wizard flattens the manager's map into a list before handing it over:

```cpp
Arinc665::Media::ConstMediaSets mediaSets{};
for ( auto [ mediaSet, checkValues ] : mediaSetManager->mediaSets() | std::views::values )
{
  mediaSets.emplace_back( std::move( mediaSet ) );
}
ui->settings->mediaSets( std::move( mediaSets ) );
```

Selecting a media set narrows the load list; selecting loads emits `loadsSelected`. Three cached members — target, media set, loads — feed `startOperation()`.

#### The load list handshake

Upload has a step the other operations do not. After the target accepts the operation, the host must send the list of loads it intends to transfer. In the CLI this is done inside the `status()` callback, guarded by a `loadListTransmittedV` flag so it fires exactly once:

```cpp
if ( ( status.code() == Arinc615a::StatusCode::OperationAccepted ) && ( !loadListTransmittedV ) )
{ ... operationV->loadList( std::move( loadsList ) ); loadListTransmittedV = true; }
```

The GUI splits the same decision across the thread boundary. The adapter's `status()` only emits; the wizard's queued slot decides whether to respond, and calls back down through `transmitLoads()` — a slot, therefore executing on the GUI thread, which then calls the core from there. The single-shot guard moves from the callback into the wizard's state.

#### Serving the files

`UploadOperation::fileRequest()` at `operations/UploadOperation.cpp:174` runs on the I/O thread and — correctly — touches no Qt widgets at all. It resolves the requested filename through `Arinc665::Media::Loads_file()`, maps it to a real path via `mediaSetManagerV->filePath( file )`, and on either failure answers the target with a TFTP error:

```cpp
operationV->errorOperation( remote, Tftp::Packets::ErrorCode::FileNotFound,
                            std::format( "File '{}' was not found.", filename ) );
```

On success it wraps the path in a `Tftp::Files::StreamFile` in `Transmit` mode, creates the transfer, binds a completion handler, and pushes it onto a `std::forward_list` of in-flight operations before starting it.

This is the one place where the GUI's file resolution differs materially from a CLI counterpart. The CLI's `AdhocUploadOperationCommand` resolves paths against a hand-supplied set of media directories; the GUI always resolves through the media set manager, which is why the *Upload Operation* action stays disabled until the startup scan finishes.

## 12 — Media Defined Download: host names the files
Four pages. The settings page is the richest in the application: target selection, download base directory, a "create download directory" toggle, a free-text user-defined-data field, and an add/remove file list backed by a `DownloadFilesModel`.

The wizard drives the operation off page transitions rather than an explicit button:

```cpp
void MediaDefinedDownloadOperationWizard::pageChanged( const int pageId )
{
  switch ( Pages{ pageId } )
  {
    case Pages::Status: startOperation(); break;
    default: break;
  }
}
```

and `startOperation()` passes four arguments rather than two — the download directory and the create-directory flag join the target:

```cpp
operationV->startOperation( targetAddressV, targetIdV, downloadBaseDirectoryV, createDownloadDirectoryV );
```

The adapter creates the directory, seeds a `Host::DownloadInformation` record, and builds the operation. When the target accepts, the wizard sends the requested file list and the user-defined data through `transmitFiles()` — the same accepted-once pattern as upload's load list.

#### Receiving

`MediaDefinedDownloadOperation::fileRequest()` at `operations/MediaDefinedDownloadOperation.cpp:207` mirrors upload's, inverted: `StreamFile` in `Receive` mode, path built from the download directory and `Helper::normaliseFilename( filename )`, and each completion recorded against the `DownloadInformation` as `TransferOk` with a byte count or `TransferError`.

`finished()` writes the download information record to disk, honouring the configuration's `verifyDownloadFiles` flag, before emitting `operationFinished`. That record is the auditable artefact of the download — the same file the CLI writes — and it is produced identically by both front ends.

## 13 — Operator Defined Download: target advertises first
The five-page outlier, and the only wizard whose middle page cannot be filled in before the operation starts.

In this operation the target tells the host what is available for download, and only then does the operator choose. So the wizard starts the operation on the way *into* the select-files page, populates `availableFiles` from a `DownloadFilesInformationModel` as the target's list arrives, and gates *Commit* on a selection existing:

```cpp
bool OperatorDefinedDownloadOperationSelectFilesPage::isComplete() const
{
  return aborted || !uiV->availableFiles->selectionModel()->selectedRows().isEmpty();
}
```

The `aborted ||` disjunction is the subtle part. Without it, an operator who aborts while the target's list is still empty would be stuck on a page whose *Commit* never enables. The flag lets the page report itself complete so the wizard can advance to the completed page and show why it stopped.

`initializePage()` reconfigures the wizard's button box for the same reason:

```cpp
wizard()->setOption( QWizard::HaveCustomButton1, true );   // "Abort Operation"
wizard()->setOption( QWizard::NoCancelButton, true );      // remove plain Cancel
```

Once the protocol is live, *Cancel* is the wrong verb — closing the dialogue does not undo a transfer in progress. Replacing it with *Abort Operation*, wired to the adapter's `abortOperation()` slot, makes the button mean what it does: send the ARINC 615A abort request and wait for the target to acknowledge it.

This page also carries its own `DownloadStatusLogModel`, so status arriving while the operator is still choosing files is not lost.

## 14 — The arinc_615a_qt model layer
A separate library from `arinc_615a_dla_qt`, and deliberately so: it depends only on `arinc_615a` and `Qt::Widgets`, carries no application state, and is reusable by any Qt program that needs to display ARINC 615A types.

| Class | Presents |
| --- | --- |
| TargetsInformationModel | FIND responses — address, target ID, THW ID, type name, position, literal name, manufacturer code |
| TargetsHardwareModel | Target hardware from a Load Configuration List file |
| PartNumbersModel | Part numbers reported by a target |
| InformationStatusLogModel | Accumulated information-operation status files |
| UploadStatusLogModel | Accumulated upload status files |
| UploadLoadsStatusModel | Per-load status within an upload — header filename, part number, ratio, code |
| DownloadStatusLogModel | Accumulated download status files |
| DownloadFilesModel | Files the operator has asked for (media defined) |
| DownloadFilesInformationModel | Files the target advertises (operator defined) |
| DownloadFilesStatusModel | Per-file status within a download |
| FindPacketStatisticModel | ARINC 615A FIND packet counters |
| ProtocolFileStatisticModel | ARINC 615A protocol file counters |

Alongside them sit `StatusCode.hpp` — a translation helper turning `Arinc615a::StatusCode` into display strings — and two dialogues, `TargetListDialog` and `TargetDetailsDialog`.

The three "status log" models are append-only. Each ARINC 615A status file the target sends becomes a row rather than replacing the previous one, which gives the operator the operation's whole history. The CLI has no equivalent; its status output is a stream.

Both Qt libraries write a stub `.clang-tidy` into their binary directories:

```cpp
file( WRITE ${CMAKE_CURRENT_BINARY_DIR}/.clang-tidy "Checks: '-*,llvm-twine-local'" )
```

That suppresses clang-tidy on AUTOMOC and AUTOUIC output, which is machine-generated and would otherwise flood the report. Worth knowing before wondering why generated sources are silent.

## 15 — Targets, settings, persistence
The application keeps two pieces of state across runs, both JSON, both in the Qt application configuration location — which is why `main()` sets the organisation name and domain before anything else.

| File | Written by | Contents |
| --- | --- | --- |
| DataLoader.json | saveDataLoaderConfiguration() | FIND configuration and timeout, ARINC 615A configuration, DLP timeout, port option, media set directory, download base directory, verify flag |
| Targets.json | saveTargets() | Target address information list — the same schema as the CLI's `--targets-list` |

`DataLoaderConfiguration` is a plain struct with `fromProperties()` / `toProperties()` over a `boost::property_tree`, embedding the core's own `Arinc615a::Arinc615aConfiguration` and `Find::FindConfiguration` objects wholesale. It is the GUI's replacement for the CLI's per-command `options_description`, and it holds exactly the same fields — the difference is that the GUI captures them once in a settings dialogue instead of on every command line.

`loadDataLoaderConfiguration()` returns a default-constructed configuration if the file is missing or unparseable, so a first run needs no setup. A separate `QSettings` key, `CheckIntegrityOnStartup` (default `true`), controls whether the media set scan verifies check values.

Persistence happens in the `DataLoaderMainWindow` destructor, after the I/O thread has been joined, and is itself wrapped in a try/catch that degrades to a warning box — a configuration write failure should not turn a clean shutdown into a crash.

## 17 — How the graphical section stands alone
Upstream, both sections build from one tree and Qt's presence alone decides whether the graphical half appears. That is convenient but implicit: there is no way to say "build the GUI and nothing else", and a CLI build on a machine that happens to have Qt installed silently acquires the Qt libraries.

This repository takes the explicit route — it *is* the graphical section. Qt is a hard requirement rather than an optional extra, declared once at the top level:

```cpp
# Qt 6 is mandatory here - this project is the graphical section only.
find_package( Qt6 REQUIRED COMPONENTS Widgets Network )
```

The `REQUIRED` is the whole statement of intent: a configure that cannot find Qt fails immediately with a clear message, rather than succeeding and quietly producing nothing. `lib/CMakeLists.txt` adds the core and the two Qt libraries; `app/CMakeLists.txt` adds the one application. There are no section switches because there is only one section.

Reaching this arrangement from the combined tree meant gating four places, and the table records what had to move — useful if you ever merge the two back together.

| File | Gated on CLI | Gated on GUI |
| --- | --- | --- |
| CMakeLists.txt | — | `qt_icon_resources` declaration and its place in `FetchContent_MakeAvailable` |
| lib/CMakeLists.txt | `arinc_615a_commands` | `arinc_615a_qt`, `arinc_615a_dla_qt` |
| app/CMakeLists.txt | `arinc_615a_operation` | `arinc_615a_data_loader_gui` |
| InstallPackage.cmake | `if( TARGET ... )` guards around each section library in the runtime-dependency directory list |  |

In this repository `lib/arinc_615a` is simply always added — it is the shared core, and the graphical section is meaningless without it.

The `InstallPackage.cmake` change is the one that is easy to miss. Its `LIBS` list originally named `$<TARGET_FILE_DIR:arinc_615a_commands>` unconditionally, and a generator expression naming a target that was never added is a hard configure error, not a warning:

```cpp
CMake Error: Error evaluating generator expression:
    $<TARGET_FILE_DIR:arinc_615a_commands>
  No target "arinc_615a_commands"
```

The fix is to build the list conditionally:

```cpp
if( TARGET arinc_615a_commands )
  list( APPEND LIBS $<TARGET_FILE_DIR:arinc_615a_commands> )
endif()

if( TARGET arinc_615a_qt )
  list( APPEND LIBS $<TARGET_FILE_DIR:arinc_615a_qt> )
endif()

if( TARGET arinc_615a_dla_qt )
  list( APPEND LIBS $<TARGET_FILE_DIR:arinc_615a_dla_qt> )
endif()
```

#### What isolation actually buys

The build sizes are the measurement. A GUI-only configure produces **306** Ninja edges to reach `arinc_615a_data_loader_gui`; a CLI-only configure produces **214** to reach `arinc_615a_operation`. Neither set contains any part of the other section — no `arinc_615a_commands` in the GUI build, no `arinc_615a_qt` in the CLI build — and the CLI configure resolves five `FetchContent` dependencies instead of six.

## 18 — Building the GUI section
#### Getting Qt

The upstream `vcpkg.json` offers a `with-qt` feature pulling `qtbase` and `qtsvg`. It works, and it compiles Qt from source — hours, and tens of gigabytes of build trees. The prebuilt binaries are the better trade here:

```cpp
python -m pip install aqtinstall
python -m aqt install-qt windows desktop 6.8.3 win64_msvc2022_64 -O <prefix>/Qt
```

76 seconds, and it matches the MSVC 14.44 toolchain the rest of the tree uses.

> **Gotcha**  
> Adding `-m qtsvg` fails with *"The packages ['qtsvg'] were not found while parsing XML of package information"*. Qt SVG is part of the base package for 6.8.3 — install without the module argument and `Qt6Svg` is present in `lib/cmake` regardless.

#### The preset

`msvc-static-debug-gui` in `cmake/presets/CMakePresetsMsvc.json` inherits `msvc-base`:

```cpp
"cacheVariables": {
  "VCPKG_APPLOCAL_DEPS": "OFF",
  "CMAKE_PREFIX_PATH": "$env{QT6_DIR}",
  "CMAKE_COMPILE_WARNING_AS_ERROR": "False",
  "CMAKE_BUILD_TYPE": "Debug"
}
```

The Qt prefix comes from an environment variable rather than a hard-coded path so the preset stays portable. The build preset restricts targets to `arinc_615a_data_loader_gui`, which is what keeps the ARINC 665 GUI applications — also made available by `FetchContent` — out of the build.

Warnings-as-errors is relaxed for this preset because AUTOMOC and AUTOUIC generated translation units and the Qt headers do not survive `/W4 /WX`. This is a property of building Qt code with this toolchain, not of the section split.

#### Result

306 build steps, no errors, producing a 29 MB debug executable at

`cmake-build-msvc-static-debug-gui/app/arinc_615a_data_loader_gui/arinc_615a_data_loader_gui.exe`.

> **Path length**  
> CMake warns that object paths for the three ARINC 665 GUI applications under `_deps/arinc_665-build/app/` reach 215–219 characters against a 250-character `CMAKE_OBJECT_PATH_MAX`. They are warnings, and those targets are outside the build set, so the GUI build is unaffected. Building the full ARINC 665 application set from this location would need a checkout nearer the drive root.

## 19 — Deploying and launching
A freshly built executable will not start from the build tree — two sets of runtime libraries are missing.

#### Qt

```cpp
"$QT6_DIR/bin/windeployqt.exe" --debug --no-translations --no-opengl-sw \
  cmake-build-msvc-static-debug-gui/app/arinc_615a_data_loader_gui/arinc_615a_data_loader_gui.exe
```

Copies `Qt6Cored`, `Qt6Guid`, `Qt6Widgetsd`, `Qt6Networkd`, `Qt6Svgd` and `D3Dcompiler_47`, plus five plugin directories: `platforms` (`qwindowsd`), `styles` (`qmodernwindowsstyled`), `imageformats` (`qsvgd`, `qicod`, `qjpegd`), `tls` and `networkinformation`. The `qsvgd` plugin is the one that matters most — without it the application runs but every icon is blank.

#### vcpkg

`msvc-base` sets `VCPKG_APPLOCAL_DEPS=OFF`, so Boost, libxml++, spdlog and their dependencies are not copied next to the executable. Put `cmake-build-msvc-static-debug-gui/vcpkg_installed/x64-windows/debug/bin` on `PATH` — nineteen DLLs including the Boost `-mt-gd-x64-1_92` set, `libxml2`, `xml++-vc143-5.0-1` and `spdlogd`.

`scripts
un-gui.bat` does this and launches; `build.bat` at the repository root chains configure, build, deploy and run in one command.

#### First run

The window comes up with three empty statistic group boxes, a menu bar of *Targets / Operations / Manage*, and three toolbars. *Upload Operation* and *Manage Media Sets* are greyed until the media set scan finishes. Diagnostics go to `%TEMP%/arinc_615a_data_loader_gui.log` at `info` level.

Confirming the stack end to end takes one FIND query: *Targets → FIND Query*, accept the broadcast address, *Commit*. After the receive timeout, *Finish* enables; closing the wizard refreshes the statistics and the FIND TX table shows the request that went out.

## 20 — Same protocol, different driver
For anyone arriving from the CLI trace, the mapping is one-to-one.

| CLI | GUI | Shared |
| --- | --- | --- |
| FindQueryCommand | FindQuery + FindQueryWizard | Find::Clients::Query |
| InformationOperationCommand | InformationOperation + wizard | Host::InformationOperation |
| UploadOperationCommand / Adhoc… | UploadOperation + wizard | Host::UploadOperation |
| MediaDefinedDownloadOperationCommand | MediaDefinedDownloadOperation + wizard | Host::MediaDefinedDownloadOperation |
| OperatorDefinedDownloadOperationCommand | OperatorDefinedDownloadOperation + wizard | Host::OperatorDefinedDownloadOperation |
| ListTargetsCommand | TargetListDialog | Find::TargetsAddressInformation |

Every row shares the third column verbatim. The GUI adds no protocol behaviour and removes none; a packet capture of an information operation is indistinguishable between the two.

#### Where each is the better tool

The CLI wins on scripting and on batch upload — `BatchUploadOperationCommand` and `UploadLoadsOperationCommand` have no GUI equivalent, and the GUI has no headless mode. It also wins on reproducibility: a command line is a record of exactly what was done.

The GUI wins on discovery and on long operations. Broadcast address enumeration, a retained status log rather than a scrolling stream, per-file and per-load progress tables, and target details persisted between sessions all matter more as an operation gets longer and as the operator gets less familiar with the equipment.

They are not alternatives so much as two front ends kept honest by a shared core — which is exactly why the section split is worth making explicit in the build.

## 21 — Observations from the trace
Three things worth recording. None blocked the build or the run.

#### 1. Qt widgets constructed on the I/O thread

> **Thread affinity**  
> Qt requires that `QWidget` instances be created and used only on the GUI thread. Three code paths violate this.

`DataLoaderMainWindow`'s I/O thread body wraps `ioContext.run()` in two catch blocks, and both call `QMessageBox::critical` followed by `QApplication::exit()` — from the I/O thread:

```cpp
ioThread = std::jthread{ [ this ] {
  try { ioContext.run(); }
  catch ( const boost::exception &e ) {
    QMessageBox::critical( nullptr, tr( "ARINC 615A I/O Task Exception" ), ... );
    QApplication::exit(); }
  catch ( ... ) { ... } } };
```

The same pattern appears in `MediaDefinedDownloadOperation::finished()` (line 193) and `OperatorDefinedDownloadOperation::finished()` (line 194) — both are handler callbacks, therefore both run on the I/O thread, and both raise a message box in their catch blocks.

All three are error paths, which is why they do not show up in normal operation. The fix in each case is the same shape the rest of the file already uses: emit a signal and let a queued slot on the GUI thread show the dialogue.

The remaining fifteen `QMessageBox` call sites in `operations/` are inside `startOperation`, `abortOperation`, `transmitLoads` and `transmitFiles` — all slots invoked from the GUI thread, all correct.

#### 2. isComplete() emits a signal

`FindQuerySelectAddressPage::isComplete()` is a `const` predicate that Qt calls whenever completeness might have changed, and it emits `targetAddressChanged` as a side effect on its success path. It works — the receiver only caches the value — but a query method that fires signals is fragile: Qt makes no promise about how often it calls `isComplete()`. Emitting from the combo box's `currentTextChanged` handler instead would be equivalent and self-evidently safe.

#### 3. Statistics refresh only on wizard close

The main window's counters update solely from wizard `finished` signals. During a long upload, the operator sees no packet activity on the main window at all — the wizard's own progress tables are the only live feedback. Defensible, given the alternative is polling process-global counters concurrently with the I/O thread writing them, but it does mean the main window's tables are a post-hoc summary rather than a monitor. Worth knowing before reading them as live.

#### Not a defect

The FIND address combo box shows its default `255.255.255.255` against a red-orange background on first display. That is the Windows 11 dark-theme text-selection colour on pre-selected combo text, not a validation failure — `isComplete()` accepts the value and *Commit* is enabled.
